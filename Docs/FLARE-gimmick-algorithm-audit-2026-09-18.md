# 宣言型GLBギミック：アルゴリズム点検・負荷改善

対象は `feature/gimmick-metadata-runtime` のGLBギミック経路。既存RAC2/VAT/パーティクルのフォーマット・復元経路は変更していない。

## 確認した破綻と修正

- **移動中の再操作で位置上限を越える**：旧実装は前フレームのTransformで上限判定し、その後 `Move` 内で進行中Tweenを現在時刻へ進めていた。判定位置と次のTween開始位置が異なる。現在は一度だけ現在時刻をサンプリングし、同じ位置から算出した移動先を検査する。拒否しても既存Tweenは壊さない。
- **書き出しでルートのスケールが消える**：位置・回転の原点正規化に加えてスケールまで1へ書き換えていた。ルート自身のlocalScaleを保持し、非一様・負のスケールも子のTransform、メッシュ、Colliderと一緒に復元する。エクスポート対象外の親Transformは取り込まない。
- **テクスチャ準備を繰り返すと増量する**：同じRGBAデータを毎回BINへ追記していた。準備済み領域の寸法・範囲・stride・実バイト列を検証し、同一データは再利用する。PNG/JPEGが変更されていれば再生成する。変更前の未参照領域を一般GLBから削除するコンパクターではない。
- **共有リソースを別物として数える**：同じUnity Material/Textureの参照でも毎回定義・画像を追加し、8 material / 4 texture制限へ誤って到達していた。エクスポート中に参照を重複排除。ランタイムでも同じmaterial定義を共有する。
- **GLBの省略値にテンプレートの状態が混ざる**：baseColor/textureがないとワールド側テンプレートの色・画像・UV変換を引き継いでいた。glTFの省略値である白・テクスチャなし・UV等倍へ明示的に初期化する。
- **入力の不正型を未指定扱い**：トップレベルの配列を型検査し、例えば文字列の `extensionsRequired` を空配列として見逃さない。asset.versionを確認。RGBAにはstrideを認めない。setActiveはBooleanまたは0/1に限定し、未登録音声はコンパイル時に無視として計上する。

## 負荷改善

| 処理 | 修正前 | 修正後 |
|---|---|---|
| 静止中のノード更新 | 全ノードへ毎フレームUdon呼び出し | 0回。動作中のノードだけを登録・解除 |
| イベント連鎖 | 各イベントで全Actionを走査、文字列比較 | 読み込み時にイベント別の連結リスト・整数命令へコンパイル。連鎖先も解決済み |
| 音声ID検索 | 再生のたびにallowlistを検索 | 読み込み時に解決しAudioClip参照を保持 |
| メッシュの数値復元 | 1ノードの全頂点・法線・UV・indicesを同じイベント内で処理 | 既定128要素/継続、Inspectorの `MeshElementsPerFrame` で16〜512へ変更可能 |
| Meshへの配列設定 | 各配列の設定を一度に実行 | ネイティブの配列設定を別々の継続へ分離 |
| リソース | material/textureの重複生成 | 同じ定義・参照を共有 |

2,048頂点・法線・UVと12,288 indicesの場合、従来は18,432要素を同じUdonイベント内で数値復元していた。修正後は既定128要素まで。ただしこれは**要素数の上限の比較であり、FPSや処理時間が144倍改善したという測定ではない**。

常駐InterpreterのUpdate自体は残るが、静止時は早期returnする。Tweenを動かした後に対象を非表示にしてもホストが補間を続ける。イベントの同一グループ内では宣言順を維持し、emitEventは従来と同じ幅優先・有限キューである。

## 検証方法と残る制限

`AvatarCatalog.Remote.FlareGimmickRegression.RunNetworkBatch` をUnity 2022.3.22f1 / ClientSimのコンパイル済みUdon VMで実行する。通常の外部GLB取得、保存済みUI接続、Interact、Tween、音声参照、再読込、異常入力に加え、以下を回帰試験へ追加した。

- 進行中Tweenをサンプルする直前の位置を故意にずらし、再操作が20mのローカル位置上限を越えないこと。
- 動いている2ノードだけが登録され、完了後の静止期間にはノードTickが増えないこと。
- イベントの一致する5操作だけを訪問すること、循環が有限で終わること。
- 非一様・負のルートスケール、共有material/texture、再準備のバイト単位での同一性。
- 2,048頂点・12,288 indicesでの分割復元、三角形順序と法線・UVの維持。
- 数値復元中にCLEAR→再読込しても古い処理が混ざらないこと。
- 不正な配列型、RGBA stride、範囲外の末尾indexの拒否。
- 色・テクスチャ・UV変換を持つテンプレートを指定しても、GLB側の省略値が優先されること。NORMAL/UVなしのメッシュも、以前のロードの属性を引き継がないこと。

### 実行結果

2026-09-18 15:25 JST、`RunNetworkBatch` **67 assertions PASS / Network=True**（Editor書き出し検査＋実Udon VM）。最終ログは `Library/FlareGimmickAudit-final.log`、結果は `Library/FlareGimmickRegression.result`。

大きいメッシュを含む5ノード試験の実カウンターは `peak elements=128, chunks=152, idle ticks=0`。152継続のうち144が2,048頂点・12,288 indicesのノード、残り8が2つの小さな立方体の属性/indices復元。実描画のドア回転前後も確認した。通常ケースでは実行時Udon例外なし。拒否試験のParse failedログは期待どおり。

Prefab再生成の既存Udon/Odin `ArgumentNullException (unityObject)` は今回も記録された。保存済みPrefabのUI接続・実行は試験を通ったが、この保存ログの原因解消までは含めていない。

JSONパース、テクスチャのアップロード、UnityネイティブのMesh API自体は分割できていない。全端末で一定ms以下になる保証はない。分割により1フレームの負荷を抑える代わりに、読み込み完了までのフレーム数は増える。経過時間・VR実機FPSの改善率は未測定。

VRChatクライアント/ヘッドセット、クリーンな新規Unityプロジェクトへの導入はこの自動試験の範囲外。Prefab生成時の既存Udon/Odin保存例外についても、アルゴリズム修正とは分けて扱う。
