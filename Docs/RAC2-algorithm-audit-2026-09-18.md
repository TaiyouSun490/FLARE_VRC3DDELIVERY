# RAC2 アルゴリズム・性能点検（2026-09-18）

この文書は修正前の点検記録です。修正内容・現在の検証範囲は [修正記録](RAC2-algorithm-fixes-2026-09-18.md) を参照してください。

## 範囲と検証の限界

現行 Creator、RAC2 v2/v3 ランタイム、VAT/Particle shader、手元の RAC2 ファイルを読み取り点検した。製品コードは変更していない。
数値検証は Python でのバイナリ解析と実装の数式の再現であり、今回新たに Unity / VRChat 上で性能を計測したものではない。
Library/Rac2CompositeUdonPlayModeTest.result にある Maria 95.3 秒の PASS は 2026-08-14 の過去記録であり、現時点のベンチマークとしては扱わない。

## 1. P1: 順次復元した VAT ノードの開始時刻が揃わない

根拠: Runtime/Rac2RuntimeLoader.cs:2221, 2815 と Shaders/Rac2VatOpaque.shader の vert。

1 ノードずつ別フレームで復元する一方、各マテリアルの _VatStartTime に復元時点の Time.timeSinceLevelLoad を設定している。最終的にまとめて表示しても、先に作った身体と後に作った服などの再生位相がずれる。非ループでは、表示前に再生が進んでしまう。
16 ノード・60 FPS・各ノード 1 フレームであれば、先頭と末尾の開始時刻差は約 0.25 秒（処理停止があればさらに増える）。これは実機計測値ではなく処理順からの例示。

修正方針: 全ノードの復元完了後、表示を有効化する前に、すべての VAT マテリアルへ同一の開始時刻を設定する。
回帰条件: 身体と服に同一周期の大きな変形を与え、2/16 ノード、ループ/非ループ、低 FPS で一致を確認する。

## 2. P1: VAT ベイクが renderer/親 Transform のアニメーションを保持しない

根拠: Editor/Rac2CreatorWindow.cs:367-420。

各フレームでは BakeMesh の renderer ローカル頂点を格納するが、ノードの LocalPosition/LocalRotation/LocalScale は全サンプリング後に 1 回しか取得しない。
renderer またはその親の移動・回転・スケールが Clip で変わる場合、その変化を全フレーム共通の末尾側 Transform で置き換えてしまう。renderer Transform が一定で、ボーンだけが動くケースとは区別する必要がある。

修正方針: 各フレームの頂点を固定した展示座標系へ変換して保存するか、ノード Transform のアニメーションも保存・再生する。前者では法線の変換も整合させ、意図した root motion の扱いを明示する。
回帰条件: renderer 自身/親だけを動かす Clip、ボーンだけを動かす Clip、非一様スケールを含む階層について、元の各フレームと復元結果を照合する。

## 3. P1: 適応予算がメッシュ復元の処理量を制限していない

根拠: Runtime/Rac2RuntimeLoader.cs:1187-1219, 1460, 2221, 2374-2580, 2625-2827。

FPS で変化する予算は解凍トークン数とチェックサムのバイト数。ContinueBundleRestore でも予算を更新するが、復元側は固定の 1 ノードで、頂点・属性・三角形・全マテリアル・テクスチャ転送まで分割されない。
最大 40,000 頂点/120,000 インデックスを含むノードも 1 イベントで処理する。このため、非圧縮化しても長い停止や VM 時間制限への到達可能性が残る。今回その最悪ケースの VM 超過を実測したわけではない。
また 0.25 秒超のフレーム時間を過去の平均値で置換しており、大きな停止を適応制御が直接評価できない。

修正方針: 頂点・属性・インデックスの解析を再開可能な段階へ分け、1 フレームの作業量を制限する。テクスチャ転送と Mesh 適用を別段階にし、分割不能な単体 API 呼び出しの負荷は別途計測する。複数ローダー同時使用時には総予算も考慮する。
回帰条件: 1 大メッシュ/16 小メッシュ、圧縮/非圧縮、上限頂点数、複数ローダーで、総時間だけでなく最大フレーム時間とフレーム時間分布を記録する。

## 4. P2: LZ4 の「トークン数」は処理時間の上限にならない

根拠: Runtime/Rac2RuntimeLoader.cs の DecompressLz4Slice。

外側だけが tokenBudget で制限され、リテラル長/一致長の拡張バイト読み取りやコピーは途中で中断できない。1 トークンでも長い処理を含められる。例として 32 MiB のリテラル長は約 13 万バイトの長さ拡張を要する。これは入力規模の例で、通常の書き出しデータがこの最悪形になるという意味ではない。

修正方針: 入力バイト・出力バイトまたは時間を併用した予算とし、長さ読み取り/リテラルコピー/一致コピーの途中状態を保持する。負荷平準化と総時間短縮は別々に評価する。
回帰条件: 長いリテラル、長い一致、distance=1 の重複コピー、切れた拡張列を含め、分割位置を変えても復元が一致することを確認する。

## 5. P2: テクスチャの重複格納・重複生成

根拠: Editor/Rac2BundleBinaryExporter.cs:362 以降、Runtime/Rac2RuntimeLoader.cs:1022 以降と ParseBundleMaterials。

マテリアルごとに画像全体を埋め込み、ロード時も個別の Texture2D を作成する。同一画像の共有テーブルがない。
手元の Maria WProp J J Ong-fast.rac2 を実際に解析した結果:

- ファイル全体: 14,351,794 bytes（約 13.69 MiB）
- モデル: 2 ノード、9,623 頂点と 94 頂点
- 画像: 2 個、画像ペイロードの SHA-256 は一致、ユニーク画像は 1 個
- 重複: 4,194,320 bytes（画像ヘッダー込み）
- 共有参照化した場合の概算: 約 9.69 MiB、約 29.2% 削減（新しい参照テーブルの費用を除く、非圧縮時）

GPU への二重転送と Texture2D の二重生成も削減できる。圧縮後サイズや総ロード時間の改善率は別途計測が必要。
texture.Apply(false, false) により CPU 側読み取り用データも維持されるため、復元後に CPU 読み取りしない画像は Apply(false, true) の利用可能性も検証する。

修正方針: まず書き出し側で画像内容・色空間・用途を含めて共通リソース化し、ロード側で共有する。既存 v2/v3 の互換を壊さない形式拡張が必要。
回帰条件: 同じ画像を複数ノードで共有、同一ピクセルでも異なる色空間、異なる normal/albedo 用途、Clear/再読込で二重破棄しないこと。

## 6. P2: 粒子の再生結果と定常負荷

根拠: Runtime/Rac2ParticlePlayer.cs:91, 107, 141-184 と Shaders/Rac2ParticleAlpha.shader の billboard 分岐。

- 初期化末尾の SpawnOne は無条件であり、EmissionRate=0 でも 1 粒出現する。
- 速度を更新してから位置を積分するため軌道が FPS に依存する。重力 9.81、初速ゼロ、1 秒後の数式再現値は 30 FPS で -5.0685 m、90 FPS で -4.9595 m。解析解は -4.905 m。実際のブース内ではクリッピング時刻にも影響する。
- Billboard では AngularSpeed の回転を Transform へ適用せず、shader 側にもその回転角を渡していないため、回転設定が見た目に反映されない。
- 最大 128 粒それぞれに個別 material を作り、毎フレーム Transform、HasProperty、色、フレーム、表示状態を書き換えている。CPU/Udon 呼び出しと描画負荷の改善余地が大きい。実際の draw call 数は未計測。

修正方針: 放出ゼロを尊重し、出生時刻・初速から位置を解析的に求める。Billboard の回転も shader に渡す。まず HasProperty 判定と不変値をキャッシュし、次に GPU 側で位置/色/flipbook を評価する方式を検討する。
回帰条件: 放出ゼロ、重力ゼロ/正負、15/30/90 FPS、非ループ終端、放出上限、Billboard の回転、再読込後の初期化。

## 7. P2: Adler32 が標準値と一致しない互換性上の負債

根拠: Editor/Rac2BinaryExporter.cs:798、Runtime/Rac2RuntimeLoader.cs の ContinueIncrementalChecksum と Adler32。

5552-byte ブロックを signed int で累積し、オーバーフロー後の符号付き剰余を使用する。現行の書き出しと読み込みはこの挙動を揃えているため、直ちに現行同士が不一致になるという指摘ではない。
実装の整数演算を再現して標準 zlib.adler32 と比較すると、0xFF を 5552 個並べた入力では現行 0xF0BD9B8C、標準 0xF18F9B8C となる。
将来別言語のエンコーダーやチェックサム高速化に置き換える際、標準実装をそのまま使うと互換性が崩れる。

修正方針: 既存ファイル向け処理を維持し、新しい版では正しい非負の剰余演算を使用する。黙って現行方式を置換しない。
回帰条件: 既存 Maria/Sakura、0xFF 連続、5552-byte 境界、任意のフレーム分割境界で旧/新それぞれの期待値を固定する。

## 推奨順序

1. VAT の開始時刻統一と座標系の修正。
2. メッシュ解析・画像反映まで含むフレーム分割と停止時間の実測。
3. テクスチャ共有化、CPU 読み取り用コピーの解放。
4. 粒子の時間依存処理修正と呼び出し削減、必要に応じた GPU 化。
5. LZ4 の作業量制限改善と、チェックサム互換性を明示した形式更新。

改善率を判定する際は、ダウンロード、解凍、チェックサム、メッシュ解析、画像転送、表示開始後の粒子更新を分けて計測する。Python や通常 C# の速度を Udon VM の速度に換算しない。
